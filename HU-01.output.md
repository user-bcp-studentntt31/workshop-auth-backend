## Summary
- Strengthen `POST /auth/login` to issue a signed token with mandatory minimum claims and consistent expiration metadata.
- Align security, configuration, testing, and evidence for the authentication flow.
- Keep the technical decision explicit on whether to retain current HMAC signing or adopt a JWT library.

## Scope (in/out)
- **In scope**
  - Enforce token claims `sub`, `client`, `iat`, and `exp`.
  - Read `client` from the request, validate it, and include it in the token.
  - Ensure `expiresIn` matches `exp - now` within a documented tolerance.
  - Remove default secret outside lab contexts or document it as lab-only.
  - Prevent logging of token, secret, and sensitive values.
  - Add tests for valid login, invalid credentials, and expired token.
- **Out of scope**
  - Any endpoint changes beyond `POST /auth/login` are not confirmed by the HU.
  - Mandatory migration from HMAC to a JWT library is not confirmed by the HU.
  - Additional claims beyond `sub`, `client`, `iat`, and `exp` are not confirmed by the HU.

## Assumptions
- The HU applies to the current authentication implementation of `POST /auth/login`.
- `AUTH_TOKEN_SECRET` remains the configured secret source for token signing.
- A tolerance value for `expiresIn` validation will be defined before implementation closure.
- The requested evidence artifacts are required for completion.

## Technical decisions to make
- Decide whether to keep HMAC signing or adopt a JWT library.
- Define exact validation rules for `client` (format, allowed values, and failure behavior).
- Define and document the tolerance value for validating `expiresIn` against `exp - now`.
- Decide how non-lab environments must provide and rotate `AUTH_TOKEN_SECRET`.

## Risks and mitigations
- **Risk:** Token or secret values exposed in logs.  
  **Mitigation:** Sanitize logging, prohibit sensitive fields in auth logs, and verify through log evidence checks.
- **Risk:** Time skew or implementation drift causes `expiresIn` inconsistency with `exp`.  
  **Mitigation:** Define explicit tolerance and enforce it with automated tests.
- **Risk:** Weak or undefined `client` validation leads to incorrect token context.  
  **Mitigation:** Document contract-level validation rules and cover valid/invalid scenarios in tests.
- **Risk:** Default secret used outside lab environment.  
  **Mitigation:** Enforce environment-specific configuration policy and document lab-only exception.

## Acceptance criteria
- Tokens from valid login contain claims `sub`, `client`, `iat`, and `exp`.
- `expiresIn` is consistent with `exp - now` within the documented tolerance.
- Automated tests cover valid login, invalid credentials, and expired token behavior.
- Authentication logs do not include token values, secret values, or sensitive values.
- The HMAC-vs-JWT technical decision is documented in the delivery evidence.

## Validation plan
- **Unit tests**
  - Validate token claim presence: `sub`, `client`, `iat`, `exp`.
  - Validate `expiresIn` coherence with `exp - now` under defined tolerance.
  - Validate error behavior for invalid credentials and expired token.
- **Functional tests**
  - Execute valid login flow and verify response fields and claim set.
  - Execute invalid credential flow and verify expected rejection behavior.
  - Execute expired-token scenario and verify expected rejection behavior.
- **Security (minimum checks)**
  - Inspect auth-related logs to confirm absence of token/secret/sensitive values.
  - Verify secret configuration policy for lab vs non-lab environments is documented and applied.
- **Required evidence (what to attach)**
  - Test outputs for claims, expiration, and authentication error scenarios.
  - Updated configuration note for `AUTH_TOKEN_SECRET`.
  - Redacted log evidence proving sensitive values are not logged.
  - This generated HU-based checklist document.
